# EFEX Secure Software Factory - Audit Evidence Guide

## Purpose

This guide helps auditors navigate the security evidence generated by the EFEX Secure Software Factory pipeline. It maps regulatory requirements to specific evidence artifacts.

---

## 3. SARIF Evidence Deep Dive

### 3.1 Understanding SARIF Structure

```json
{
  "$schema": "https://raw.githubusercontent.com/oasis-tcs/sarif-spec/master/Schemata/sarif-schema-2.1.0.json",
  "version": "2.1.0",
  "runs": [{
    "tool": {
      "driver": {
        "name": "Semgrep",
        "version": "1.45.0",
        "rules": [
          {
            "id": "efex-sql-injection-transfer",
            "shortDescription": { "text": "SQL Injection in financial query" },
            "fullDescription": { "text": "..." },
            "defaultConfiguration": { "level": "error" },
            "properties": {
              "cwe": "CWE-89",
              "owasp": "A03:2021"
            }
          }
        ]
      }
    },
    "results": [
      {
        "ruleId": "efex-sql-injection-transfer",
        "level": "error",
        "message": { "text": "SQL injection vulnerability detected" },
        "locations": [{
          "physicalLocation": {
            "artifactLocation": { "uri": "vulnerable-app/main.py" },
            "region": { "startLine": 67, "startColumn": 5 }
          }
        }]
      }
    ]
  }]
}
```

### 3.2 Key SARIF Fields for Auditors

| Field | Description | Audit Use |
|-------|-------------|-----------|
| `tool.driver.name` | Scanner tool | Which tool found the issue |
| `tool.driver.rules` | Policy definitions | What was checked |
| `results[].ruleId` | Policy violated | Link to control |
| `results[].level` | Severity | Risk assessment |
| `results[].locations` | File and line | Remediation tracking |
| `properties.cwe` | CWE reference | Industry standard mapping |
| `properties.owasp` | OWASP reference | Industry standard mapping |

### 3.3 Querying SARIF with jq

```bash
# Count findings by severity
cat semgrep.sarif | jq '[.runs[].results[] | .level] | group_by(.) | map({level: .[0], count: length})'

# List all unique rule IDs
cat semgrep.sarif | jq '[.runs[].results[].ruleId] | unique'

# Get all high severity findings
cat semgrep.sarif | jq '.runs[].results[] | select(.level == "error")'

# Find findings in specific file
cat semgrep.sarif | jq '.runs[].results[] | select(.locations[].physicalLocation.artifactLocation.uri | contains("main.py"))'
```

## 4. SBOM Evidence Deep Dive

### 4.1 SPDX SBOM Structure

```json
{
  "spdxVersion": "SPDX-2.3",
  "dataLicense": "CC0-1.0",
  "SPDXID": "SPDXRef-DOCUMENT",
  "name": "efex-transfer-service",
  "documentNamespace": "https://efex.com/sbom/...",
  "creationInfo": {
    "created": "2024-01-15T10:00:00Z",
    "creators": ["Tool: syft-0.98.0"]
  },
  "packages": [
    {
      "SPDXID": "SPDXRef-Package-python-fastapi",
      "name": "fastapi",
      "versionInfo": "0.109.0",
      "supplier": "Organization: FastAPI",
      "downloadLocation": "https://pypi.org/project/fastapi/",
      "filesAnalyzed": false,
      "licenseConcluded": "MIT",
      "externalRefs": [
        {
          "referenceCategory": "PACKAGE_MANAGER",
          "referenceType": "purl",
          "referenceLocator": "pkg:pypi/fastapi@0.109.0"
        }
      ],
      "checksums": [
        {
          "algorithm": "SHA256",
          "checksumValue": "abc123..."
        }
      ]
    }
  ],
  "relationships": [
    {
      "spdxElementId": "SPDXRef-DOCUMENT",
      "relationshipType": "DESCRIBES",
      "relatedSpdxElement": "SPDXRef-Package-python-fastapi"
    }
  ]
}
```

### 4.2 Key SBOM Fields for Auditors

| Field | NTIA Minimum | Purpose |
|-------|--------------|---------|
| `name` | ✅ Required | Component identification |
| `versionInfo` | ✅ Required | Vulnerability correlation |
| `supplier` | ✅ Required | Supply chain tracking |
| `checksums` | ✅ Required | Integrity verification |
| `externalRefs.purl` | ✅ Required | Package URL for lookup |
| `licenseConcluded` | Recommended | Compliance |

### 4.3 Querying SBOM with jq

```bash
# List all packages
cat sbom.spdx.json | jq '.packages[] | {name, version: .versionInfo}'

# Count packages
cat sbom.spdx.json | jq '.packages | length'

# Find packages by license
cat sbom.spdx.json | jq '.packages[] | select(.licenseConcluded == "MIT") | .name'

# Get package URLs (PURLs)
cat sbom.spdx.json | jq '.packages[].externalRefs[] | select(.referenceType == "purl") | .referenceLocator'
```

## 6. Common Auditor Questions

### Q: How do you ensure scans run on every commit?
**A:** The GitHub Actions workflow triggers on all pushes to main and feature branches, plus all pull requests. See `.github/workflows/security-pipeline.yml` line 10-14.

### Q: Can developers bypass the security gates?
**A:** No. Branch protection rules require all status checks to pass. The `security-gate` job is a required check that fails if any upstream security job fails.

### Q: How long do you retain evidence?
**A:**
- SARIF files: 90 days (GitHub Actions artifact retention)
- SBOM files: 1 year (S3 lifecycle policy)
- Container signatures: Indefinitely (Rekor transparency log)

### Q: How do you handle false positives?
**A:**
1. Inline suppressions with documented justification
2. Baseline files for known issues
3. Waiver workflow with approval trail
See `docs/adr/ADR-002-policy-as-code-strategy.md` for details.

### Q: How do you verify signature integrity?
**A:**
```bash
cosign verify \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/efex/api@sha256:...
```

## Appendix: Evidence File Checksums

Generate integrity checksums for evidence package:

```bash
cd evidence
sha256sum *.sarif *.json > CHECKSUMS.sha256
```

Verify:
```bash
sha256sum -c CHECKSUMS.sha256
```
